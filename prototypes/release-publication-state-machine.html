Release Publication State Machine

The question. What concrete version and publication state machine turns each qualifying production-business push to main into exactly one retry-safe stable GitHub Release, keeps tag, assembly, package metadata, ZIP, checksum, Release, and root manifest.json consistent, avoids recursive releases from manifest maintenance, retains supported history, and handles concurrent runs, partial failure, rerun, withdrawal, and rollback?

Press buttons and watch the state. Every button is always available; the machine refuses whatever is not legal right now and says why. The refusals are the interesting part.

Proposed decisions baked into this model — react to these

  1. Version authority. The next version is computed only after entering the release queue, as the highest of (main's committed version files, every Release tag ever published, every manifest entry, every withdrawn version) plus a patch bump. So failed CI, docs pushes, and withdrawn versions never consume or reuse a number.
  2. Version files are committed. One additive maintenance commit carries both the manifest entry and the bumped build.yaml/csproj version, pushed after publication. The alternative derives versions at build time and leaves main permanently at 1.0.0.0.
  3. Pin the triggering push. A transaction ships the head SHA of its own push, not whatever main looks like at dequeue; the maintenance commit merges additively onto the newer head.
  4. Lost evidence adopts, not stalls. On retry with no recorded digest but a complete attached asset whose embedded identities match the pinned version, the publisher adopts that asset's digest as authoritative. The alternative fails closed forever, which strands a published Release.
  5. Withdrawal needs a ledger. A committed withdrawal ledger beside manifest.json is the only durable "do not resurrect" record, so a retry can tell "manifest commit failed, repair it" from "deliberately withdrawn, leave it out".
  6. Retries jump the queue. A failed transaction returns to the front of the serialized queue and reconciles from published evidence; it never starts a second Release.
  7. First release is 1.0.1.0. The committed-but-unpublished 1.0.0.0 is a floor, not a release. The alternative publishes 1.0.0.0 first.
