Race-safe preview cache

Does a two-level coordination model—a shared cache-tree lease for requests, a short exclusive lease for empty-directory pruning, and one keyed lock per final preview path—keep requests and scheduled cleanup safe under every required race?

Throwaway prototype · not production code

Proposed decisions to pressure-test

The demo implements these claims so awkward sequences can be driven by hand. A claim should be changed if a walkthrough produces an outcome that feels wrong.

Per-preview ownership

Requests and cleanup must hold the keyed lock for the final cache path before reading, publishing, or deleting that preview or its temporary file.

Snapshot cleanup

Cleanup deletes only files observed when its run starts and only if their fingerprint is unchanged. A newly generated preview survives until the next run.

Buffered responses

The response owns JPEG bytes in memory before releasing the keyed lock, so later deletion cannot break an in-flight HTTP response.

Cancellation is local

If the generating request is cancelled, it removes its temporary file and releases ownership. A waiter retries and may become the next generator.

Short tree exclusion

File sweeping remains per-path and concurrent. Only bottom-up empty-directory pruning takes an exclusive tree lease; new requests wait briefly and then recreate directories if needed.

Boundary refusal

Requests fail closed at a symlink/reparse-point boundary. Cleanup skips and warns; it never traverses that boundary.
